GitHub Workflow

Git tracks history; GitHub adds collaboration on top — forks, pull requests, reviews, issues, and automation. This page covers how those pieces fit together.

If a reviewer requests changes, you push more commits to the same branch and the loop continues — no need to open a new PR.

Forking vs. cloning

CloneFork
What it doesCopies a repo to your local machineCopies a repo to your own GitHub account
When you'd use itYou already have push access (e.g. a team repo, a GitHub Classroom repo)You don't have push access to the original (e.g. contributing to someone else's open-source project)
Typical next stepBranch, commit, push directlyBranch, commit, push to your fork, then open a pull request back to the original

For most course assignments you'll clone a repo you already have access to. Forking matters more once you're contributing to a shared or external project.

Pull requests

A pull request (PR) proposes merging one branch into another and gives everyone a place to discuss and review the change before it lands.

  1. Push your branch: git push origin feature/login-form
  2. On GitHub, open Pull requests → New pull request, choose your branch, and describe what changed and why.
  3. Reviewers leave comments, request changes, or approve.
  4. Push more commits to the same branch to address feedback — they show up in the same PR automatically.
  5. Once approved, merge the PR (usually via the "Squash and merge" or "Merge" button on GitHub).
Tip

Write PR descriptions for a reader who has zero context: what does this change, why was it needed, and how did you test it? "Fixed bug" tells a reviewer nothing.

Code review etiquette

  • As an author: keep PRs small and focused — a 30-line PR gets a careful review, a 900-line PR gets a rubber stamp. Respond to every comment, even if it's just "done" or "good point, didn't change this — here's why."
  • As a reviewer: comment on the code, not the person ("this loop re-fetches on every iteration" vs. "you did this wrong"). Distinguish blocking issues from nitpicks — say so explicitly if a comment is optional.
  • It's fine to approve with minor suggested changes rather than blocking a PR on style preferences.

Issues

Issues track bugs, tasks, and discussion separate from any specific branch. A good issue includes: what's wrong or wanted, steps to reproduce (for bugs), and what you expected instead.

Link a PR to an issue so it closes automatically on merge by including a keyword in the PR description:

Fixes #42
Closes #17

GitHub Actions (a quick intro)

Actions run automated workflows — most commonly, running your test suite on every push or PR so problems are caught before merging. A minimal example, saved as .github/workflows/tests.yml:

name: Run tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: pytest

If your course uses autograding via GitHub Classroom, this is the same mechanism under the hood — your PR or push triggers a workflow that runs your tests and reports pass/fail.

Troubleshooting cheat sheet

SymptomLikely cause & fix
Updates were rejected because the remote contains work that you do not have locally Someone pushed since you last pulled. Run git pull (resolve conflicts if prompted), then push again.
Permission denied (publickey) or a 403 on push Your credentials aren't set up. Check you're using HTTPS with a token, or that your SSH key is added to your GitHub account under Settings → SSH keys.
You are in 'detached HEAD' state You checked out a commit or tag directly instead of a branch. If you want to keep any new work: git switch -c new-branch-name before doing anything else.
Committed straight to main by accident Move the commit to a new branch without touching main: git branch feature-name, then git reset --hard origin/main on main, then git switch feature-name.
Merge conflict markers showing up in a file See Resolving merge conflicts.
Accidentally committed a large or sensitive file If it hasn't been pushed yet: git reset --soft HEAD~1, remove the file, recommit. If it has been pushed, stop and ask a TA — rewriting pushed history needs care.
