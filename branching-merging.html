Branching & Merging

A branch is just a movable pointer to a commit. Branching lets you work on something — a feature, a fix, an experiment — without touching the code everyone else is relying on.

Why branch

Without branches, every commit lands on the same line of history, so half-finished work is visible (and risky) for everyone. With branches, you isolate your changes until they're ready, then bring them back together with a merge.

Creating & switching branches

# List branches (current one is marked with *)
git branch

# Create a new branch
git branch feature/login-form

# Switch to it
git switch feature/login-form

# Create and switch in one step
git switch -c feature/login-form

# Delete a branch you're done with (once merged)
git branch -d feature/login-form
Tip

You may see git checkout -b <name> in older tutorials — that's the predecessor to git switch -c. They do the same thing; switch is just less overloaded and harder to use by mistake.

Merging

To bring a branch's changes into your current branch:

git switch main
git merge feature/login-form

Git resolves this one of two ways:

  • Fast-forward: if main hasn't moved since you branched off it, git just slides the pointer forward. No new commit, no conflict possible.
  • Three-way merge: if both branches have new commits, git combines them and creates a new "merge commit" with two parents. This is where conflicts can happen.

Resolving merge conflicts

A conflict happens when the same lines were changed differently on both branches, and git can't guess which version you want. When it happens, git pauses the merge and marks the file:

<<<<<<< HEAD
your version of the code
=======
their version of the code
>>>>>>> feature/login-form

To resolve it:

  1. Open the file and decide what the final code should look like — keep one side, the other, or a combination.
  2. Delete the <<<<<<<, =======, and >>>>>>> marker lines entirely.
  3. Stage the resolved file: git add <file>
  4. Finish the merge: git commit (git pre-fills a merge commit message for you).
Tip

Run git status at any point during a conflict — it lists exactly which files still need resolving. If it all goes wrong, git merge --abort backs out and returns you to how things were before you ran merge.

Rebasing

Rebasing rewrites your branch so it looks like you started from the current tip of another branch, instead of where you actually branched off:

git switch feature/login-form
git rebase main

This replays your commits one by one on top of main, which gives a cleaner, linear history than a merge commit would. But it rewrites commit history — the commits get new hashes.

MergeRebase
Preserves history exactly as it happenedRewrites history into a straight line
Adds an extra merge commitNo merge commit, cleaner log
Safe on shared/public branchesSafe only on branches nobody else is using
Warning — the golden rule of rebasing

Never rebase a branch that other people have already pulled or branched from. Rewriting shared history means everyone else's copy diverges from yours, and untangling it is far more painful than the merge commit you were trying to avoid.

Best practices

  • Keep branches small and focused on one thing — easier to review, easier to merge, easier to abandon if it doesn't work out.
  • Name branches descriptively: fix/null-pointer-in-parser, not george-branch-2.
  • Pull the latest main before you start a new branch, so you're not conflicting with changes you didn't know about.
  • Commit often within a branch — small commits are easier to review and easier to revert individually if one turns out to be wrong.
